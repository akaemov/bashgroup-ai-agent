# Техническое задание: кабинет агентов БАШГРУПП

Статус: требования из интервью с разработчиком и согласованное направление продукта. Уточнения для рабочей системы ниже отмечены как предлагаемые. История — [PROJECT_CONTEXT.md](../PROJECT_CONTEXT.md).

## 1. Назначение и границы

Создать единый русскоязычный кабинет для коммерческого управления: исследования, конкуренты, рынок, проекты/заказчики, закупки, подготовка и согласование КП.

Азат — основной пользователь и главный оркестратор. Он принимает решения, агенты выполняют отдельные функции и работают по настроенным сценариям. Разработчик управляет технической частью.

Первая поставка — демонстрационный UI (готов). Следующая — рабочее серверное хранение и первый рабочий агент **подготовки коммерческих предложений**. Прежний приоритет разведки заменён. UI следует развивать в одобренном стиле, без переосмысления его в чат-приложение. [Подробный план КП](PROPOSALS_AGENT.md).

## 2. Пользователи и права

| Возможность | Азат | Разработчик | Сотрудник в будущем |
|---|---|---|---|
| Бизнес-результаты | Полный доступ в своём пространстве | По настроенным правам сопровождения | По задачам |
| Ручной запуск | Да | Для проверки и сопровождения | По назначению |
| Конкуренты, темы, источники | Да | Для настройки | По назначению |
| Бизнес-согласования | Основное лицо | Не подменяет решение Азата | Если делегировано |
| Скиллы, код, API, модели | Нет | Да | Нет по умолчанию |
| Техническая диагностика | Не основа бизнес-UI | Да | По необходимости |
| Изменение расписания | Требует уточнения | Техническая настройка | Требует уточнения |

Фактическая аутентификация и серверная реализация прав ещё отсутствуют. Роли БД — технические аккаунты, а не роли пользователей кабинета.

## 4. UX

1. Главное — исследования и коммерческая полезность, не техническая активность.
2. Дашборды/отчёты приоритетнее форм, формы приоритетнее чата.
3. Сначала вывод, затем детали/доказательства, затем действие.
4. В разведке наиболее заметны профиль, рекомендации и сравнения.
5. Решение можно вернуть с конкретным объяснением.
6. «Неизвестно», «не проверено», «ошибка загрузки» и «не существует» — разные состояния.
7. Демо и реальные сведения различимы.
8. Desktop-first. Полная мобильная версия — отдельный этап.

## 5. Нефункциональные требования

- История версий и происхождения выводов.
- Права проверяются на сервере, не только видимостью кнопок.
- Ключи провайдера и пароли БД не попадают во frontend/Git.
- Длительная работа не зависит от открытой вкладки.
- Ограниченные retries, контроль стоимости и журнал ошибок.
- Повтор запуска/отправки не создаёт дубли.
- Повреждение одного источника не стирает последнее подтверждённое значение.
- Закрытые данные доступны только после настройки входа/HTTPS и правил использования.
- Точные SLA, бюджет, объём нагрузки и сроки хранения надо согласовать; цифры не заданы.

## 6. Контракт первого агента

### 6.1. Подготовка КП — текущий приоритет

Предлагаемые входные группы: запрос клиента и вложения; номенклатура/спецификация; единицы и количество; версия прайса и правила расчёта; комплектация; условия; шаблон; ограничения и неизвестные.

Предлагаемые выходные группы: разобранные требования, выбранные позиции и основания, воспроизводимый расчёт, пробелы/вопросы, черновик, версия документа, решение Азата и файл в выбранном формате.

Тип первичного запроса, продуктовый периметр, схема и формат выдачи ещё не выбраны. Отдельный скилл КП предстоит разработать. Цены и арифметику задаёт программа по утверждённым данным; модель помогает разбору и тексту. Формальная JSON Schema и API ещё не определены. Следующие миграции должны учитывать запросы, позиции, версии КП и согласования.

### 6.2. Конкурентная разведка — задел следующего направления

Сохранённая методика — [оригинальный SKILL.md](../competitor_agent/skills/SKILL.md). Этот скилл не является инструкцией агента КП.

#### Вход разведки: логические группы

`run_id`, `mode`, `period`, `timezone`, `as_of`, `question`, `bashgroup_materials`, `company_registry`, `source_plan`, `documents_current`, `documents_previous`, `fetch_results`, `known_events`, `known_claims`, `constraints`.

#### Выход разведки: логические группы

`run_id`, `analysis_status`, `material_coverage`, `identity_updates`, `profile_updates`, `evidence`, `claims`, `events`, `comparisons`, `conclusions`, `recommendations`, `conflicts`, `corrections`, `coverage`, `errors`, `specialist_reviews`, `report`.

Это **предлагаемый контракт скилла**, не существующее HTTP API и не формальная JSON Schema. Поля, enums, null и ссылки нужно утвердить при реализации. Существующие таблицы не покрывают каждую группу целиком.

## 7. Требования аналитики

- Проверять доступность каталога и фактическое прочтение кейсов.
- Идентифицировать кандидатов, не приписывать чужие сайты/роли.
- Существенный тезис связывать с реально полученным документом и фрагментом.
- Разделять заявления, подтверждённые факты, выводы и гипотезы.
- Не считать перепечатки независимыми источниками.
- Сравнивать сопоставимые исполнения, комплектацию и условия.
- Не придумывать экономику, параметры, даты и рыночные показатели.
- Техническую эквивалентность передавать специалисту с конкретным вопросом.
- Сохранять противоречия и покрытие, исправлять историю явно.
- Документы не могут менять инструкции агента или инициировать действия.

## 8. Межагентный сценарий

Для первого рабочего релиза КП запрос передаётся Азатом/менеджером вручную. Приоритетная цепочка: запрос → проверка полноты → подбор и расчёт → черновик → решение Азата → документ. Тип входа ещё согласуется. Готовность остальных агентов не является зависимостью этого запуска.

В дальнейшем сохраняется межагентный сценарий:

```text
Разведка / заказчики / закупки
→ проверка релевантности и неизвестного
→ контекст и источники для агента КП
→ черновик с подтверждёнными параметрами
→ проверка Азата
→ согласовано / доработка / отказ
→ отправка только точного согласованного документа и получателя
→ журнал результата
```

Рабочая отправка, каналы и техническая процедура ещё не реализованы. Изменение содержания/получателя после согласования требует повторного решения.

## 9. Критерии приёмки

### Прототип

- Доступ по IP, открываются пять направлений.
- Пользователь проходит отчёт → основания → решение без технических объяснений.
- Работают карточки, фильтры, комментарии и передача в КП.
- Показаны границы демо, нет реальных отправок.
- Сохранено одобренное визуальное направление.

### База данных: выполненный этап

- Автозапуск, локальный listener, раздельные роли.
- Миграция повторяемая, seed идемпотентный.
- Runtime не имеет DDL/админ-прав.
- Проверены FK/unique/CHECK и отсутствие тестовых записей.
- Ежедневный backup и восстановление с совпадением данных.

### Первый рабочий агент КП: предлагается согласовать

1. Вход и авторизация.
2. Реальный запрос выбранного типа и вложения сохраняются на сервере.
3. Запрос корректно разбирается; неизвестные параметры явно отмечены.
4. Подбор и цены основаны на подтверждённых данных и их версиях.
5. Программный расчёт совпадает с эталонами по единицам, НДС, скидкам и округлению.
6. Черновик соответствует шаблону; формат файла выбран и согласован.
7. Доработки создают новую версию и сохраняют комментарии.
8. Решение Азата относится к точной версии и хранится на сервере.
9. Повтор не создаёт дубли; автоматическая отправка не считается подключённой.
10. Азат подтвердил полезность на согласованных примерах «запрос → КП».

Для последующего агента разведки отдельно остаются baseline, evidence/покрытие и 18 сценариев его оригинального скилла.

## 10. Объём следующих релизов

Типовой запрос/эталоны КП → шаблон и правила расчёта → скилл/контракт КП → API/авторизация/версии → YandexGPT + программный расчёт → черновик и согласование → выходной документ → отдельно отправка → разведка и другие агенты → расписания/роли/дополнительный экспорт/mobile/chat.

Точный объём MVP и порядок последующих направлений зависят от ответов Азата. Готовый скилл есть только у разведки; скилл первого агента КП и требования других новых направлений ещё надо подготовить.
