# Конкурентная разведка: гриллинг MVP

Дата начала: 2026-11-06.
Цель: разобрать первый пользовательский сценарий, определить границы MVP и подготовить основания для функциональных требований и брифа совместной сессии с напарником.

## Подтверждённые решения

- Первый приоритет — переход конкурентной разведки из демосценария в MVP.
- Исследуем существующий продукт локально и постепенно уточняем требования.
- Метод обсуждения — гриллинг: один вопрос за раз, рекомендация для обсуждения, фиксация каждого ответа.
- Нужен бриф для совместной сессии пользователя и напарника на выходных.
- YandexGPT выбран пользователем как провайдер модели.
- MVP: ручной запуск исследования конкретного конкурента и повторное исследование для обновления данных.
- Повторный запуск сохраняет историю отчётов и показывает сравнение (diff): изменения, улучшения, ухудшения и отсутствие изменений. Критерии оценки и точка сравнения ещё не определены.
- В дальнейшем предусмотреть расписания, возможно отдельные для каждого конкурента. Cron предложен пользователем как пример, техническое решение не выбрано.
- Повторное исследование сравнивается с последним завершённым исследованием этого конкурента. Выбор произвольной версии не согласован.
- В MVP исследуется весь профиль конкурента по единой структуре; выбор отдельных тем — дальнейшее развитие.
- Источники MVP включают официальный сайт конкурента и внешние источники. Механизм обнаружения и пределы поиска ещё не согласованы.
- Источники обнаруживаются автоматически; пользователь также может добавлять собственные ссылки.
- Поиск должен следовать заданной методике: категории источников и шаблоны запросов/ключевых слов. Пользователь назвал официальные сайты, карты (2GIS, Яндекс) и соцсети как примеры. Точный обязательный набор и техническая доступность ещё не определены.
- Перед первым исследованием пользователь подтверждает найденную компанию: название, официальный сайт, регион и связанные ресурсы; может исправить найденные данные. Подтверждённая идентичность сохраняется для повторных запусков.
- При недоступности части источников показываем результат со статусом «Завершено с ограничениями» и явным списком непроверенных вопросов и недоступных источников. Недоступность источника не считается исчезновением продукта или ухудшением предложения.
- «Завершено с ограничениями» становится базой следующего сравнения. Сравниваем проверенные данные; не обновлённые значения сохраняем с датой последней проверки и пометкой «Не удалось обновить», без вывода об изменении.
- Если исследование недостаточно полноценное, присваиваем статус «Завершено с ошибкой». Порог достаточности определим позже; он не ограничен случаем полного отсутствия данных.
- Ошибочные запуски сохраняются в истории с причинами, но исключаются из базы сравнения. Следующее исследование сравниваем с последним результатом «Завершено» или «Завершено с ограничениями».
- Результат представлен постоянным актуальным профилем конкурента и отдельным сохранённым отчётом каждого запуска. Отчёт показывает проверенное в запуске, изменения и пробелы; профиль — актуальные сведения с ранее согласованными пометками свежести.
- У каждого существенного факта по нажатию раскрываются источник, подтверждающий фрагмент и дата проверки. В профиле факт показывается кратко.
- При противоречии источников показываем обе версии с источниками, объяснением расхождения и пометкой «Требует проверки»; без достаточных оснований одну версию не выбираем.
- Глубина изучения продукции в MVP — продуктовые семейства: назначение, основные характеристики, варианты исполнения и документы. Полный разбор каждой товарной позиции в MVP не включён.
- Первый отчёт включает сравнение конкурента с БАШГРУПП: пересечения продуктовых семейств, различия в подтверждённых характеристиках, услугах и документации. Нехватка сведений о БАШГРУПП показывается как пробел, а не отсутствие предложения.
- Перед первым исследованием показываем дату и состав базы знаний БАШГРУПП (сейчас каталог и 20 кейсов), предлагаем подтвердить использование или добавить актуальные материалы.
- Рабочий подход для проверки в MVP: каталог и кейсы БАШГРУПП задают ориентиры поиска и основу сравнения, но не ограничивают разведку существующими направлениями. Агент отмечает также новые для доступных материалов БАШГРУПП направления конкурента. Отсутствие аналога в материалах не означает отсутствие компетенции компании.
- Пользователь может сообщить об ошибке в конкретном факте кнопкой «Сообщить об ошибке» с комментарием. Замечание сохраняется рядом с фактом и учитывается при повторном исследовании; исходный результат остаётся в истории.
- Прогресс MVP: текущий фактический этап, прошедшее время на этом этапе и общее прошедшее время исследования с запуска. Оценку оставшегося времени (ETA), диапазоны и проценты готовности не показываем.
- Исследование выполняется на сервере независимо от открытой вкладки. После возвращения пользователь видит актуальный прогресс или готовый результат.
- Для каждого конкурента допускается только одно активное исследование. Пока оно выполняется, вместо повторного запуска показываем «Открыть текущий запуск», предотвращая дубли.
- В MVP есть «Остановить исследование»: прекращаем дальнейшую обработку, сохраняем запуск со статусом «Остановлено пользователем» и исключаем его из базы сравнения. Уже отправленный запрос к модели может завершиться; возможность его отмены зависит от API.
- После ошибки или остановки повтор исследования запускает только пользователь вручную. Создаётся новый запуск с начала; предыдущая попытка сохраняется в истории. Автоматический повтор всего исследования и продолжение с места остановки в MVP не включены.
- Во время обновления последний сохранённый профиль остаётся доступен с пометкой «Идёт обновление». Новый результат публикуется после завершения; ошибка или остановка прежний профиль не заменяет. Для результата с ограничениями действуют согласованные правила сохранения не обновлённых значений.
- Результаты «Завершено» и «Завершено с ограничениями» автоматически обновляют профиль без отдельного согласования. Проверка фактов доступна через источники и действие «Сообщить об ошибке».
- В MVP пока нет уведомлений, включая внешний канал и отдельные уведомления внутри кабинета. Статус и результат доступны при просмотре исследования.
- В MVP включена выгрузка полного отчёта конкретного запуска в PDF: дата и статус исследования, краткие выводы, профиль конкурента по результату этого запуска, сравнение с БАШГРУПП, изменения относительно предыдущего базового исследования, источники и пробелы. Документ должен быть понятен отдельно от кабинета.
- Повторное исследование автоматически проверяет ранее найденные источники и дополнительно ищет новые страницы, проекты и каналы конкурента. Это поведение внутри вручную запущенного исследования, а не автоматический запуск по расписанию.
- Ручное исключение источника из будущих исследований (действие «Не использовать») в MVP не включаем. Проверка релевантности и принадлежности источников системой остаётся частью методики.
- В начале профиля показываем краткую сводку перед подробными разделами: специализация конкурента, пересечения с БАШГРУПП, основные подтверждённые отличия, дата исследования и ограничения. После обновления сводка включает ключевые изменения. Рекомендации этим решением не согласованы.
- При добавлении конкурента название обязательно, официальный сайт необязателен. Система ищет компанию и показывает найденные данные для подтверждения перед первым исследованием.
- При нескольких одноимённых компаниях показываем варианты с названием, сайтом, регионом и краткой специализацией. Если подходящего варианта нет, пользователь уточняет название или добавляет ссылку; исследование ждёт выбора и подтверждения.
- Упрощение MVP: совпадение названия с существующим профилем считается дублем независимо от сайта. Новый профиль не создаётся; показываем ошибку «Профиль компании с таким названием уже существует». Автоматический переход в профиль не согласован. Выбор одноимённых компаний при внешнем поиске сохраняется, но два профиля с одинаковым названием в MVP не допускаются.
- При проверке дублей названия сравниваем без учёта регистра и лишних пробелов: обрезаем пробелы по краям, последовательности пробелов внутри сводим к одному. Иные преобразования (ООО, кавычки, транслитерация) не согласованы.
- Удаление и архивирование конкурентов в MVP не включаем.
- Работа ведётся в отдельной ветке discovery/competitive-intelligence-mvp. Пользователь поручил запушить изменения в конце работы; развёртывание на VPS этим не согласовано.

## Проверенные исходные факты

- Исходная версия: cf2ecda, main; README, PROJECT_CONTEXT.md и docs/TECHNICAL_SPEC.md.
- UI содержит кандидатов, профили, сравнения, рекомендации и отчёты.
- start() в ui/src/main.tsx имитирует выполнение таймерами; результат заранее подготовлен.
- В форме исследования тема и агент сохраняются в состоянии React; режим и контекст не передаются в start().
- Добавление кандидата сохраняет только название в памяти; введённый сайт не сохраняется.
- Добавление источника показывает уведомление, без загрузки и сохранения.
- Профили и сравнения пока содержат заглушки. Решения сохраняются в localStorage.
- Есть методика первого агента и слой БД; рабочего HTTP API и вызовов модели нет.
- Состояние удалённого VPS в этой сессии не проверялось.

## Предлагаемый порядок исследования — не согласованные требования

1. Определить первое полезное бизнес-решение, которому помогает разведка.
2. Пройти текущий интерфейс: кандидат → задача → результат → источник → решение.
3. Выбрать узкий объём MVP: компании, продукция, источники, тип исследования.
4. Уточнить входные данные, результат, ошибки, неизвестное и обратную связь.
5. Записать проверяемые критерии приёмки и примеры полезных ответов.
6. Подготовить бриф: ответы, гипотезы, вопросы напарнику и нужные материалы.
7. На этой основе уточнить функциональные требования и последовательность реализации.

## Журнал вопросов и ответов

### Q1 — Решение после исследования

- Вопрос: какое конкретное решение Азат должен уметь принимать после исследования конкурентной разведки?
- Ответ пользователя: «Пока я тебе ответ на этот вопрос не даю», вопрос нужно зафиксировать в брифе и продолжить обсуждение.
- Статус: отложен до совместной сессии пользователя и напарника; ответ не согласован.
- Гипотеза ассистента для обсуждения: выбор изменения в ассортименте, документации или аргументации продаж. Не считать требованием или границей MVP.
- Флаг: цель результата остаётся открытой; не выбирать зависящие от неё функции окончательно.

### Q2 — Текущий процесс изучения конкурентов

- Вопрос: как Азат сейчас изучает конкурентов и как выглядел последний реальный случай поиска информации?
- Ответ пользователя: «выноси в бриф».
- Статус: отложен, добавлен в раздел 2 брифа; сведений о текущем процессе пока нет.
- Не предполагать конкретный процесс, участников или затраты времени без ответа.

### Q3 — Ручной запуск, обновление и история

- Вопрос: начать с исследования конкурента по запросу или регулярного мониторинга?
- Ответ: «в MVP мы включим запуск исследование конкурентно по запросу»; нужна кнопка обновления/повторного исследования.
- Пользователь подчеркнул: повторное исследование должно сохранять историчность отчётов и показывать сравнение — «что изменилось, что стало лучше, что стало хуже, что осталось без изменений».
- Дальнейшее развитие: настройка расписания, возможно индивидуального для каждого конкурента; cron приведён как пример.
- Открыто: что сравнивается, с какой версией и с чьей точки зрения оцениваются улучшения/ухудшения. Поведение при ошибках загрузки ещё не обсуждалось.

### Q4 — Базовая версия для сравнения

- Вопрос: с чем сравнивать повторное исследование?
- Ответ пользователя: «с последним завершенным иследованием».
- Решение: сравнивать с последним завершённым исследованием того же конкурента.
- Не добавлять выбор произвольной версии как согласованную функцию. Правила частично завершённых запусков ещё не определены.

### Q5 — Объём исследования

- Вопрос: исследовать весь профиль или выбирать отдельные темы?
- Ответ пользователя: «давай исследование всего профиля. в последствии можно будет уже внедрить выбор отдельных тем».
- Решение: MVP исследует весь профиль по единой структуре; выбор отдельных тем отложен.
- Состав блоков предусмотрен существующим скиллом; глубину и пределы сбора ещё предстоит определить.

### Q6 — Внешние источники

- Вопрос: ограничить MVP официальным сайтом и его документами или включить внешние источники?
- Ответ пользователя: «внешние источники тоже включаем».
- Решение: включить внешние источники наряду с официальным сайтом.
- Не определены: автоматический поиск или ручной список, категории и пределы источников, глубина и бюджет сбора. Не считать конкретный поисковый сервис выбранным.

### Q7 — Обнаружение источников и методика поиска

- Вопрос: автоматический поиск внешних источников или заранее заданный список ссылок?
- Ответ: автоматический поиск и возможность добавить свои ссылки.
- Пожелание пользователя: «чтобы агент не каждый раз гадал, а куда бы ему еще сходить»; описать набор направлений поиска в промпте: официальные сайты, карты (2GIS, Яндекс), ключевые слова, соцсети.
- Решение: формализовать методику поиска; точный набор источников/запросов уточнить. Примеры не считать подтверждением наличия интеграций или доступа.
- Предложение реализации для обсуждения: хранить версию плана поиска, найденные ресурсы и фактическое покрытие; промпт задаёт правила, программные инструменты выполняют поиск и загрузку.

### Q8 — Подтверждение идентичности компании

- Вопрос: подтверждать правильность найденной компании перед первым исследованием, сохраняя идентичность для повторных запусков?
- Рекомендация: показать название, официальный сайт, регион и найденные связанные ресурсы; дать подтвердить или исправить.
- Ответ пользователя: «да давай».
- Решение: включить этот шаг перед первым исследованием и сохранять подтверждённую идентичность для последующих запусков.
- Уточнение: подтверждение идентичности не означает автоматическое подтверждение конкурентности, фактов из источников или принадлежности будущих найденных ресурсов.

### Q9 — Неполное покрытие и недоступные источники

- Вопрос: показывать результат по доступным данным или считать исследование незавершённым, если часть источников недоступна?
- Ответ пользователя: «завершено с ограничениями»; «явно фиксировать список этих пробелов, список того, что не удалось посмотреть, или список того, куда нам не удалось залезть».
- Решение: выдавать доступный результат с указанным статусом и явным перечнем пробелов/недоступных ресурсов.
- Принятая рекомендация: недоступность источника при сравнении не считать исчезновением продукта или ухудшением предложения.
- Открыто: участие такого результата в выборе последнего завершённого исследования для следующего сравнения; поведение при отсутствии пригодных данных вообще.

### Q10 — Базовая версия при ограничениях

- Вопрос: становится ли исследование «Завершено с ограничениями» базой для следующего сравнения?
- Рекомендация: да; сравнивать только проверенные данные, при недоступности источника сохранять прежнее значение с датой последней проверки и пометкой «Не удалось обновить», без вывода об изменении.
- Ответ пользователя: «да».
- Решение: рекомендация принята целиком. Сохранённое прежнее значение не считается заново подтверждённым; пробел нельзя показывать как «без изменений».
- Открыто: поведение при полном отсутствии пригодных данных.

### Q11 — Ошибка при недостаточной полноте

- Вопрос: считать ли исследование ошибкой, если вообще не получено пригодных данных?
- Ответ пользователя: «если исследование там вообще неполноценное, этот порог неполноценности мы, наверное, определим позже, то будем считать его завершенным с ошибкой».
- Решение: статус «Завершено с ошибкой» при недостаточной полноценности исследования; критерии и порог отложены.
- Не считать согласованными предложенные ранее кнопку повтора и правила базовой версии для ошибочного запуска: пользователь явно подтвердил статус и необходимость позже определить порог.
