# PostgreSQL — первый рабочий слой БАШГРУПП

Эта поставка создаёт БД и миграции. Backend API, авторизация, workers и подключение UI будут следующими этапами. Браузер напрямую к PostgreSQL не подключается.

Первый рабочий агент теперь — **подготовка КП**. Начальная схема и скилл разведки сохраняются как общий задел, но не определяют текущую очередь. Запросы, позиции, расчёты, версии КП и согласования потребуют отдельного контракта и следующих миграций. [План КП](../docs/PROPOSALS_AGENT.md).

## Устройство

- PostgreSQL 16 из Ubuntu 24.04, системный сервис с автозапуском.
- База `bashgroup`, схема `app`, только localhost:5432 и Unix socket.
- `bashgroup_owner` — NOLOGIN-владелец схемы и таблиц.
- `bashgroup_migrator` — вход для миграций, NOINHERIT, явный `SET ROLE bashgroup_owner`.
- `bashgroup_app` — runtime CRUD без DDL, superuser, создания БД, truncate и управления ролями.
- У runtime нет прав изменять `alembic_version`.
- Приложение не использует PostgreSQL superuser.

Секреты: `/etc/bashgroup/database.json` (root:root, 0600; каталог 0700). Файл не копируется в Git или UI. Пока приложение не установлено, runtime-пароль также хранится в этом root-only конфиге. При создании API дать его системному пользователю **только runtime**-реквизиты отдельным файлом; не передавать API migrator-пароль.

## Миграции

На VPS под root:

```sh
/opt/agents/bashgroup-ai-agent/.venv/bin/alembic -c /opt/agents/bashgroup-ai-agent/backend/alembic.ini current
/opt/agents/bashgroup-ai-agent/.venv/bin/alembic -c /opt/agents/bashgroup-ai-agent/backend/alembic.ini upgrade head
/opt/agents/bashgroup-ai-agent/.venv/bin/python /opt/agents/bashgroup-ai-agent/backend/scripts/seed.py
```

`provision.py` — одноразовый bootstrap. При обнаружении существующих имён или файла реквизитов останавливается. В случае частичного сбоя не удалять секреты и роли автоматически: проверить состояние вручную.

Первичная миграция: 14 предметных таблиц и `alembic_version`. Сущности: агенты, скиллы, материалы, компании, запуски, источники, попытки загрузки, версии документов, доказательства, утверждения и связи, отчёты, рекомендации, решения.

Начальные данные: 5 выключенных агентов (реальные workers ещё не настроены), 1 версия оригинального скилла, 5 неподтверждённых кандидатов, каталог и 20 кейсов. Материалы зарегистрированы с хешем и исходным текстом, но не объявлены прочитанными AI. Публичность относится к уже опубликованному каталогу/кейсам; новые закрытые материалы по умолчанию `internal`.

В текущей схеме нет полной модели пользователей, КП, событий мониторинга, расходов и оркестрации. Эти сущности добавляются следующими миграциями по согласованным контрактам. `actor_label` в решении — временное поле, не аутентификация пользователя. Наличие FK и CHECK не заменяет проверку качества доказательств и прав в API.

## Проверки

```sh
/opt/agents/bashgroup-ai-agent/.venv/bin/python /opt/agents/bashgroup-ai-agent/backend/scripts/verify.py
systemctl status postgresql@16-main
systemctl list-timers bashgroup-db-backup.timer
journalctl -u bashgroup-db-backup.service --no-pager
```

`verify.py` проверяет ограничения и права в откатываемых транзакциях, затем восстанавливает последний backup в отдельную временную БД, сравнивает содержимое, проверяет FK и удаляет только эту тестовую БД.

## Бэкапы

- Каталог `/var/backups/bashgroup`, postgres:postgres, 0700.
- Копия в custom-format `pg_dump`, файл 0600, временный файл публикуется атомарно.
- systemd timer: ежедневно 03:20 UTC с задержкой до 5 минут (примерно 06:20 МСК).
- Сохраняются 14 последних успешных файлов, включая ручные запуски (это не гарантия 14 календарных дней).
- Ручной запуск: `systemctl start bashgroup-db-backup.service`.
- Копия на том же VPS не защищает от потери VPS. Внешнее хранилище пока не предоставлено и не подключено.
- Dump содержит данные и схему, не пароли ролей и не внешние файлы. Для восстановления на новом сервере отдельно подготовить роли и конфигурацию. Реквизиты нужно хранить в отдельном защищённом backup-процессе.

## Доступ с ноутбука

```sh
ssh -i ~/.ssh/id_ed25519_arcvps -o IdentitiesOnly=yes -N \
  -L 15432:127.0.0.1:5432 root@81.222.148.50
```

Затем DB-клиент подключается к `127.0.0.1:15432`, база `bashgroup`. Реквизиты взять из защищённого серверного файла; не вставлять пароль в чат или командную строку. Публичного доступа на 5432 нет.

## Развёртывание с нуля

1. Установить `postgresql-16`, `postgresql-client-16`, `python3-venv`.
2. Настроить `listen_addresses = 'localhost'`; убедиться, что TCP-аутентификация использует scram-sha-256, а админ-доступ через Unix socket — peer.
3. Создать `.venv`, установить `requirements.lock`. В `requirements.txt` заданы допустимые диапазоны для осознанного обновления; lock фиксирует проверенную установку на Python 3.12.
4. Выполнить `scripts/provision.py`, затем миграцию и `scripts/seed.py`.
5. Создать backup-каталог с указанными правами; установить units из `deploy`, включить timer.
6. Запустить первый backup и `scripts/verify.py`.

Коммиты и push отдельно не выполнялись. Все новые файлы сначала проверить через `git status`/`git diff`.
